# FP16 精度與使用指南

v0.5.0 的三種 YOLOv8 s／640 已通過500張抽樣AP回歸，涵蓋FP32／FP16與三種圖執行模式。
對照官方FP32差距不超過0.5個百分點，見 [本版抽樣AP報告](ap_v050.md)。
v0.4.0曾執行完整COCO AP，僅作歷史記錄，見 [舊版AP報告](ap_fp16.md)。
其他模型與尺寸仍需各自驗證，不能由這三組結果推論。
完整驗證與長跑分必須由使用者明確啟動；短測不會自動接續完整測試。

預編譯發布包的安裝方式（不需要重新編譯）：

```powershell
python -m pip install .\vonnx-0.5.0-cp312-cp312-win_amd64.whl
# Runtime DLL 不在 wheel/SDK 內；可指定既有相容 DLL 目錄：
$env:VONNX_DLL_DIRS = 'C:\runtime\ort;C:\runtime\cuda;C:\runtime\cudnn'
```

## 呼叫方式

```python
from vonnx import EngineConfig, vONNXEngine
c = EngineConfig()
c.model_path = "models/yolov8s/yolov8s.onnx"
c.precision = "fp16"          # auto（預設）/ fp32 / fp16
c.batch_shape_policy = "auto" # auto / dynamic / fixed
c.imgsz = 640
# 選填：預設 %LOCALAPPDATA%/vonnx/models
c.model_cache_dir = "runs/fp16/cache"
e = vONNXEngine(c)
try:
    s = e.model_spec
    print(s.source_precision, s.effective_precision, s.converted)
    print(s.input_dtype, s.output_dtypes, s.prepared_model_path)
finally:
    e.close()
```

| 原模型 | auto | fp32 | fp16 |
|---|---|---|---|
| FP32 | 保留 | 保留 | 內部轉換 |
| FP16 | 保留 | 報錯 | 保留 |
| 混合 | 保留 | 報錯 | 依轉換規則準備 |

辨識包含 TensorProto、子圖、張量型別與 Cast 目標，不僅看模型 I/O。
本版拒絕 ONNX local functions、其他浮點型別及無法辨識精度的模型。
dtype 採 ONNX 編號：1=FP32、10=FP16；mixed 表示圖中同時存在兩者。
它不代表 GPU 每一條指令或累加器的實際精度。
靜態 batch=1 模型須設定 `max_batch_size=1`，不會自動降低使用者指定的 batch 上限。

## 執行 batch 與補零

`batch_shape_policy="auto"` 在 FP16／混合精度的吞吐模式固定以 `max_batch_size`
執行；不足的影像位置補零並丟棄輸出。原因是目前 ORT cuDNN 路徑在 batch 尺寸切換時
重建執行計畫，暖機所有尺寸仍不能保留所有計畫。固定 shape 可避免這項熱路徑成本。
相關實作可見 [ORT CUDA Conv UpdateState](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/providers/cuda/nn/conv.cc)。
FP32 和低延遲模式預設維持動態 batch；`dynamic`／`fixed` 可明確覆寫。
這項補零策略適用於逐影像獨立推論的 YOLOv8；自訂跨 batch 計算的模型須使用 dynamic。

單張低延遲用途請設定 `batch_mode="latency"`，避免為一張影像執行完整 batch。
固定策略不增加請求數、不突破 batch 上限，也不回傳補零位置的框／關鍵點／mask。
`result.batch_size` 是該批真實請求數，`result.physical_batch_size` 是實際執行尺寸；
`model_spec.fixed_batch_size` 為 0 表示動態，非零表示固定尺寸。
跑分 FPS 只計成功的真實請求，另記錄 physical_batch_histogram 與 padded_images。

## 轉換與依賴

採用 `onnxruntime.transformers.float16`，保留 FP32 I/O，YOLOv8 DFL／座標解碼保留
FP32，卷積分支與 backbone 轉成 FP16。已有 FP16 I/O 亦可直接使用。
前處理／NMS／座標還原／mask 累加與公開結果維持 FP32。

第一次初始化有轉換及 GPU shape 探測成本，後續請求不再轉換。
原始模型不覆寫；快取鍵包含來源及外部權重雜湊、工具／轉換程式版本與保留節點規則。
相同快取有跨程序鎖、內容校驗及原子寫入；失敗不默默退回 FP32。
鎖等待 120 秒，若程序被強制終止留下 `.lock`，確認無轉換程序後手動移除該鎖。
轉換子程序最多等待 180 秒，暫停／恢復不重新轉換或重建資源。

Python wheel 宣告 `onnx==1.22.0`、`onnxruntime-gpu==1.28.0` 與 numpy 依賴。
Python API 自動使用目前解譯器和隨套件的 `precision.py`。
C++／C API 直接執行 FP32／FP16 模型不需要 Python；**FP32 轉 FP16** 才需要上述
Python 依賴。SDK 必須將 `precision.py` 放在 DLL／執行檔旁，或指定 `precision_tool`；
`precision_python` 可指定解譯器完整路徑，未指定時使用 PATH 中的 `python.exe`。
本版原生自動轉換以 Windows 為支援環境。
仍需要既有 Windows x64／VC++ runtime、CUDA 13 runtime、CUDA 12 cuBLAS、
cuDNN 9 與 ORT GPU 1.28.0 的 DLL 搜尋路徑；Python wheel 為 CPython 3.12 x64。
FP16／混合模型偏好 ORT NHWC 內部布局，外部 I/O 仍是 NCHW；FP32 保持原設定。

```cpp
vonnx::EngineConfig c;
c.model_path = "yolov8s.onnx";
c.precision = "fp16";
c.precision_python = "C:/myenv/python.exe";
c.model_cache_dir = "D:/cache/vonnx";
vonnx::vONNXEngine engine(c);
```

C API v3：`vonnx_config_init_v3`、`vonnx_create_engine_v3`、`vonnx_model_info_get_v3`。
precision：0=auto、1=fp32、2=fp16。既有 v1／v2 的布局與 FP32 語意保留。
batch_shape_policy：0=auto、1=dynamic、2=fixed。
結果釋放前可用 `vonnx_result_physical_batch_v3` 查詢實際執行尺寸。
v3 handle 沿用 v1 image/result 與 v2 生命週期函式。
`examples/c_api.cpp` 示範 v3；其可選環境變數為 `VONNX_PYTHON` 與 `VONNX_MODEL_CACHE_DIR`。

SDK 解壓後，在 VS 2022 x64 Native Tools 命令列編譯與呼叫：

```powershell
cl /std:c++17 /EHsc /MD /I. c_api.cpp vonnx.lib delayimp.lib /Fe:c_api.exe /link /DELAYLOAD:vonnx.dll
$env:VONNX_PYTHON = 'C:\myenv\python.exe'
$env:VONNX_MODEL_CACHE_DIR = 'C:\cache\vonnx'
.\c_api.exe yolov8s.onnx image.rgb 640 480 fp16
```

`image.rgb` 是連續 RGB24 原始資料，可由 `load_image("image.jpg").tofile("image.rgb")` 產生。
此範例採單路低延遲／batch 1；批次併發用途請初始化 throughput、batch 8、concurrency 32，
以獨立呼叫執行緒使用同一 handle。結果必須用 `vonnx_result_free` 釋放，所有呼叫完成後
才可銷毀引擎。CUDA stream 與 GPU 輸入的生命週期規則沿用原 API。

## 小規模驗證與速度比較

以下 CLI 在原始碼目錄執行；wheel 只安裝推論模組，不包含模型／驗證工具。
SDK 的 quick_start.py 也需要已安裝 wheel，並指定自己的模型與影像路徑。

```powershell
python examples/quick_start.py --model models/yolov8s/yolov8s.onnx --precision fp16 --cache-dir runs/fp16/cache
python -m vonnx_tools optimize --phase check --precision fp16 --output runs/fp16/fp16
python -m vonnx_tools optimize --phase quick --precision fp16 --output runs/fp16/fp16
# 六個併發情境全數勝出才能執行 confirm：
python -m vonnx_tools optimize --phase confirm --precision fp16 --output runs/fp16/fp16
python -m vonnx_tools optimize --phase diagnostic --precision fp16 --output runs/fp16/fp16
```

quick：25 暖機 + 75 計分；confirm：25 暖機 + 475 計分，三輪。
測三種 s 模型、640、1／16／32 路，batch 上限 8；每輪最多五分鐘。
主要測試關閉詳細 timing，官方採相同湊批等待並使用原版 FP16 predictor。
雙方影像以各自原生格式預載：vONNX 為 RGB24、官方為 BGR24；顏色轉換不重複計入官方時間。
單路延遲另報，不能取代 16／32 路吞吐門檻。
結果含 JSONL、CSV／JSON、Markdown 與圖表；不同精度必須使用不同輸出目錄。

正確性參考使用獨立 ORT CUDA session 執行同一份準備後 ONNX，再交給官方 FP32
後處理。FP16 分數容易相同，因此驗證參考以獨立 Torch greedy NMS 實作相同的原始
索引 tie-break；效能測試的官方 NMS 不修改。此檢查證明引擎一致性，不能取代 AP 評估。
原始輸出門檻為 atol=1e-3、rtol=1e-2，匹配框／關鍵點 ≤1 pixel、mask IoU≥0.99。
本版500張抽樣AP回歸使用下列獨立指令，不會接續效能跑分：

```powershell
python tools/diagnostics/ap_release.py --resume
python tools/diagnostics/ap_release_report.py
```

ORT 的結尾同步仍保留；多引擎共享 GPU，並不提供硬體隔離。
本機 ORT/cuDNN 會在初始化嘗試計畫時輸出 `No execution plans support the graph`；
目前成功案例會接續使用後備計畫並完成推論。原始訊息保留在測試 log，未以空結果掩蓋失敗。
